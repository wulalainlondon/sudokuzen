**1．題庫載入合併：最適合先做**

啟動時有三個呼叫來源：`src/app/legacyRuntime.ts:126`、`:313`，以及 `src/react/normal/NormalStageMap.tsx:75`。`src/data/dataRegistry.ts:102` 的快取只保存「已完成」的資料，沒有保存進行中的 Promise，所以三個呼叫在首次資料回來前都各自發出請求及解析 JSON。

一般題庫約 518 KB 原始 JSON。原型加入依題庫名稱索引的 Promise Map，三個呼叫共用一次載入，請求和解析都由 3 次降為 1 次。三個入口各自的完成通知可以保留。瀏覽器可能合併 HTTP 請求或命中快取，因此這是應用層成本減少 67%，不應直接宣稱實際網路流量也必然少 67%。

正式實作還應補上資料 manifest／shard 的逾時、失敗後移除進行中快取，以及並行呼叫、網路失敗後重試測試。教學題庫已有逾時工具可參考。

**2．音效：先取消重複播放，再考慮物件池**

`src/game/core.ts:515` 在每次輸入後呼叫 `selectCell()` 更新反白；`src/game/board.ts` 的 `selectCell()` 同時播放選格音效。筆記輸入因此會播放筆記聲，再播放一次選格聲。`src/game/audio.ts:85` 每次播放都建立新的 `Audio`，並重新取得音量設定。

原型讓程式內部刷新使用無音效的選取更新，使用者真正點格子仍保留選格音效。固定 20 次筆記輸入從 40 個 Audio 物件降為 20 個。這個改法比先大幅改寫音效系統更小，後續才評估有上限的音效物件池。物件數減少已實證；真機耗電與 INP 改善尚未量測。

**3．對戰存檔：同一輸入只保存一次**

正確填數字會經過兩條路徑：

- `src/game/core.ts:504` → `recordDuoMove()` → `src/features/duo/duoGame.ts:934` 立即存檔。
- `src/game/core.ts:513` → `src/game/persistence.ts:24` → 再存同一盤快照。

10 次正確輸入共寫入 20 次，其中 10 次與上一份內容完全相同。原型合併正確輸入的寫入後，降為 10 次，固定情境的 JSON 字元寫入量從 44,362 降為 22,181。最後快照包含完整 10 步回放，81 格值也與記憶體棋盤一致。

正式改法應讓「記錄這一步」與「保存最新狀態」有明確順序。錯誤預覽結束後的延後存檔、擦除、筆記、離開前保存等路徑都要保留。應避免只拉長防抖時間而造成離開時遺失操作。原型通過現有 359 項單元測試及型別檢查，仍需要 PWA 強制關閉／恢復與對戰回放驗收。

**房間公開：仍有可造成長時間等待的寫入端缺口**

`src/features/duo/duoRoom.ts:368` 先建立 WebSocket 房間，再非同步公開到大廳。`src/features/duo/duoLobbyMirror.ts:80` 等待 Firestore `.set()` 完成，完成後才開始保鮮，只有拒絕時才重試。

隔離故障測試讓 `.set()` 永不完成；模擬 60 秒後，公開 Promise 仍未結束、只嘗試一次，且沒有保鮮寫入。讀取端的 3 秒逾時無法解決尚未寫入大廳的房間。

改善方向是為公開狀態提供明確期限與恢復途徑，或由已驗證的服務端維護公開索引。現有 `_mutationChain` 會被未完成的寫入卡住；只在外層加 `Promise.race()`，重試仍可能排在卡住的佇列後面。還必須處理「使用者已離房，早先寫入才成功」的情況，保留 epoch／晚到清理防護。這是值得優先處理的穩定性問題，但故障注入不等於已證實所有使用者等待都是這個原因。

**4–5．快取：兩個可以直接減少浪費的地方**

`src/pwa/sw.template.js:8` 仍預先快取 `levels.js`。目前 `index.html` 已移除其 script，資料入口改由 `dataRegistry` 載入 JSON shards；程式碼中剩餘檔名引用是快取、建置和 smoke 檢查。停止新版本對它的預先快取，可省下約 631 KB 原始檔案的首次安裝／更新下載與儲存。舊檔在伺服器端的相容保留可以另外處理，並同步調整建置／smoke 檢查。

`scripts/build-data.mjs:71` 使用 `crypto.randomBytes()` 產生題庫版本，`dataRegistry` 把它加到每個 shard 網址。對照兩次已發布的乾淨建置，27 份題庫合計 6,445,161 bytes 完全相同，網址卻都失效重建。題庫是按需載入，不能把 6.45 MB 當作每位玩家都會下載的浪費。

建議使用每份題庫的內容 hash，搭配獨立資料快取；同時檢查 `src/pwa/swUpdate.ts` 的刪除快取與 `sw.template.js` 的版本快取清理。只改 manifest hash、卻每次更新仍刪掉資料快取，無法完整取得跨版本重用的收益。教學題庫的建置腳本已有內容 hash 可參考。

**6．打包：目前效能預算少算了依賴**

正式 V2 入口的七個靜態 JS 相依檔合計 1,186,430 bytes，gzip 342,691 bytes；加上 CSS gzip 29,660 bytes，共 372,351 bytes。`scripts/perf-budget.mjs` 只算入口 JS 和 CSS，得到 160,862 bytes，少算約 211 KB gzip，實際靜態相依量約為報表的 2.31 倍。這裡還沒有計入之後啟動的 Firebase、字型和 JSON 題庫。

應先讓預算走訪靜態 import 圖，再拆解首屏不需要的技能註冊、世界模式 UI 等依賴。技能、世界、solver 三個檔案合計約 100 KB gzip，是需要檢查的範圍；它們含有共用程式，不能直接把整個大小當成可刪除量。延後載入的實際收益需要另做首次可操作時間的 A/B 驗證。

**本輪不列為優先的項目**

選格時 81 次候選標記查詢可以做增量更新，20 次筆記輸入目前會做 1,620 次查詢；但移除漸變後，現有選格實測已多數在下一幀完成。應等低階真機仍有主執行緒尖峰的證據，再投入較複雜的棋盤快取。單純拆大檔、改寫已為 no-op 的 `evaluateLockedSkill()`，本輪沒有可量化的優先收益。
